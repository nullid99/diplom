# Зони спостереження та часові події

Сторінки: `/analysis` — редактор зон і параметри запуску; `/events` — журнал; `/settings` — типові часові налаштування. Результати фактичних перевірок і screenshots: [reports/events/REPORT.md](../reports/events/REPORT.md).

## Запуск у Windows PowerShell

Зареєстрована YOLO11n і минулі результати збережені. Нове навчання не потрібне. API/UI можуть уже працювати — не запускайте другий екземпляр на тих самих портах.

```powershell
Set-Location D:\FireVision
# Один раз для переходу зі старої схеми (вже виконано):
.\scripts\db.ps1 -Action upgrade
# В окремих вікнах, якщо відповідний процес ще не працює:
.\scripts\start-backend.ps1
.\scripts\start-frontend.ps1
# Окремий worker; CPU за замовчуванням у формі:
.\scripts\start-analysis-worker.ps1
```

Для GPU, тільки за відсутності навчання/іншого GPU-експерименту, перед запуском API та worker задайте `$env:ANALYSIS_ALLOW_GPU='true'` у відповідних вікнах. Це змінна лише поточного процесу й нащадків. GPU-lock, PostgreSQL-черга, worker fencing, WebSocket, скасування й готові MP4/JSONL попереднього етапу збережені.

## Зони

У «Аналіз відео» оберіть джерело. Власний перегляд редактора дозволяє вибрати кадр, додати прямокутник спостереження або виключення, пересунути його, змінити нижній правий кут чи точні координати/назву з клавіатури. Правило можна переключити; область можна видалити. Потім натисніть «Зберегти зони». За незбережених або ще не завантажених зон запуск недоступний.

`video_sources.observation_zones` — JSON-масив, максимум 32 зони з унікальними id. Координати x1/y1/x2/y2 нормалізовані до [0,1], прямокутник має додатні ширину й висоту (мінімум .001). SVG розміщений **над реальною областю зображення object-fit:contain**, із врахуванням масштабування, aspect ratio та чорних полів; pointer координати перетворюються від цієї області. Чорні поля не входять у координати. Під час drag повідомлення не змінюють геометрію сторінки. На вузькому екрані геометрія переобчислюється ResizeObserver.

Рамка потрапляє в аналіз, коли її **центр** перебуває хоча б в одній включаючій зоні та не перебуває в жодній виключаючій. Виключення має пріоритет; межа прямокутника входить у зону. Без включаючих зон доступний увесь кадр за винятком виключень. Фільтрація відбувається перед часовим алгоритмом і записом прийнятих виявлень у JSONL. Відео результату зберігає всі початкові кадри й час, а не тільки ROI.

При створенні запуску сервер копіює зони джерела в `analysis_runs.settings_snapshot.zones`. Надіслані клієнтом зони не підміняють збережений конфіг джерела. Після цього зміни джерела не змінюють snapshot минулого запуску. Старі schema_version=1 запуски не отримують часові події заднім числом.

## Часовий алгоритм

Модуль `backend/app/temporal.py` не імпортує ML і не використовує час роботи worker. Вхід — прийняті рамки й **вихідні часові мітки проаналізованих кадрів**. Порожній проаналізований кадр теж передається. Кадр, пропущений детектором, не видається за негативне спостереження. Для VFR використовуються PTS, не номер кадру / середній FPS.

Для smoke і fire окремо побудовано кандидати відповідностей за IoU або близькістю центрів. Відстань — `sqrt(dx_norm² + dy_norm²)` у нормалізованій системі; при низькому IoU додатково потрібне відношення площ ≥ .2. Кандидати впорядковуються за найбільшим IoU, потім відстанню; жадібне однозначне зіставлення не призначає одну рамку двом областям. Дублюючі рамки одного класу з IoU≥.85 у тому самому кадрі зводяться до найвпевненішої. Це інженерний алгоритм просторових областей, не повноцінний трекер ідентичності об'єктів; близькі/перехресні об'єкти можуть давати неоднозначності.

Для кожної області зберігається обмежена ковзним часовим вікном історія моментів спостереження. Підтвердження вимагає N **різних кадрів** у вікні й мінімального часового розмаху. Кілька рамок одного кадру не збільшують кількість часових підтверджень. Повторні спостереження оновлюють ту саму подію до timeout. Різні просторові області можуть мати різні події. Непідтверджені короткі кандидати не потрапляють у журнал.

Початкові значення (не результат оптимізації):

| Параметр | Значення |
| --- | ---: |
| analysis_fps | 2 |
| window_seconds | 3 |
| min_hits | 3 |
| min_span_seconds | 1 |
| absence_seconds | 2 |
| match_iou | .1 |
| center_distance | .12 |
| clip_before_seconds | 2 |
| clip_after_seconds | 3 |

Перевіряється `(min_hits−1)/analysis_fps ≤ window_seconds`, `min_span_seconds ≤ window_seconds`, `absence_seconds ≥ 1/analysis_fps`, скінченність/межі параметрів. Це перевірка теоретичної узгодженості: реальні рідкі/VFR кадри не гарантують потрібної кількості спостережень. Відсутність закриває подію на `last_seen + absence_seconds`; спостереження після цього інтервалу починає нову область. На точній межі інтервалу нове спостереження ще може продовжити область. EOF закриває активні підтверджені області фактичною тривалістю відео.

`app_settings` — технічна singleton-конфігурація (ключ analysis). `/settings` зберігає defaults; новий запуск копіює їх або явно задані параметри у свій незмінний snapshot (schema_version=2). У формі аналізу параметри можна змінити для одного запуску. Конфіг джерела/запуску й оцінки оператора не навчають модель.

## Схема та життєвий цикл

Міграція `0004_zones_events` доповнює наявну `events`, не створюючи таблицю покадрових рамок:

- `start_seconds` — перше виявлення; `confirmed_seconds` — момент підтвердження;
- `last_seen_seconds` — останнє збережене позитивне спостереження;
- `closed_seconds` — момент закриття у відео, `end_seconds` зберігає той самий момент для нових завершених подій;
- `closure_reason`: absence, eof, cancelled, failed або worker_interrupted;
- `automatic_status`: confirmed під час активності, completed лише для absence/eof, interrupted при скасуванні/помилці/аварії;
- `track_key` та unique(analysis_run_id,track_key) забезпечують ідемпотентне технічне збереження; id=UUID5(run_id,track_key);
- `confidence` — максимальна впевненість області; `region` містить нормалізовану рамку підтвердження, останню рамку й часові межі фрагмента.

Час створення/редагування — timestamptz; позиції відео — numeric seconds, окремо від технічного часу. `events` пов'язана з `analysis_runs`, а через запуск — із video_sources, model_versions і settings_snapshot; source_id не дублюється.

Після підтвердження зберігається один агрегат події, далі оновлюється його last_seen/region/confidence. Це оновлення агрегату, **не вставка кожної рамки окремим рядком SQL**. Повторний upsert не скидає оцінку й коментар оператора. Власник worker перевіряється під блокуванням рядка запуску.

При відомому скасуванні/помилці закриття використовує останню фактично прочитану позицію відео. При аварії процесу без достовірного моменту зупинки API/worker recovery позначає подію interrupted/worker_interrupted і залишає closed_seconds/end_seconds NULL — час не вигадується. Останнє успішно збережене last_seen залишається. Раніше коректно закриті за absence події не стають «помилковими» через пізніший збій запуску.

## Доказові матеріали

Кадр підтвердження з рамкою і короткий **фрагмент оригінального відео**, без звуку, створюються FFmpeg CPU/H.264. Межі обмежені реальною тривалістю; для VFR бажані межі розширюються до сусідніх фактичних меж кадрів. Manifest містить source clip_start/end, confirmation offset і виміряну тривалість фрагмента. Кадр і manifest синхронізуються, відеопотік фрагмента перевіряється ffprobe, файли публікуються атомарним rename перед upsert.

Файли: `<STORAGE_ROOT>/event-evidence/<run_id>/<event_id>/frame.jpg`, `clip.mp4`, `manifest.json`; тимчасові — `storage/tmp/event-evidence/`. У БД тільки відносні шляхи. Перезапуск технічного upsert використовує ті самі id/матеріали. При невідомому результаті DB commit матеріали можуть лишитися без доступного запису як карантин; вони не видаються за готову подію. Докази вже збережених interrupted-подій доступні окремо, із чесним статусом; часткове основне відео невдалого аналізу, як і раніше, недоступне.

## API та журнал

| Метод | Адреса | Призначення |
| --- | --- | --- |
| GET / PUT | `/api/video-sources/{id}/zones` | Отримання / заміна конфігурації зон джерела |
| GET / PUT | `/api/analysis-defaults` | Типова частота та TemporalConfig для нових запусків |
| GET | `/api/events?page=1&page_size=20` | Журнал з пагінацією |
| GET | `/api/events/{id}` | Картка, region, модель, запуск, snapshot |
| PATCH | `/api/events/{id}/review` | review_status, operator_comment, expected_updated_at |
| GET | `/api/events/{id}/files/frame` або `/clip` | Матеріали за id, без довільного шляху клієнта; clip підтримує Range |

Фільтри журналу: source_id, feature_type=smoke/fire, review_status, since/until. Період фільтрує **дату реєстрації події**, а не секунди відео. API вимагає timezone, UI перетворює local datetime у ISO timestamp. Оцінки: unreviewed/confirmed/false_positive/needs_review. Автоматичний стан від них не змінюється. Конкурентне редагування виявляється за expected_updated_at; HTTP409 вимагає повторного відкриття картки.

API, що має `/test/model`, теж існує лише в test app. Тестова БД видаляється; screenshot із заповненим журналом позначено TEST-ONLY.

`scripts/events-browser-real.mjs` — окрема **не read-only** перевірка на робочих API/UI: тимчасово зберігає зони й defaults та відновлює попередні значення в finally; не створює подій/моделей/запусків. Вона потребує джерела без збережених зон. У звичайний check-events її не включено.
