# FireVision

Система дозволяє завантажувати, перевіряти та переглядати відеоджерела, запускати аналіз окремим YOLO worker, отримувати WebSocket-прогрес, відео з рамками й JSONL. Повне навчання YOLO11n завершено (50 епох), фінальні ваги перевірено та зареєстровано. Реальний наскрізний сценарій також пройдено на природних неперервних FIRESENSE відео: 10 базових інтервалів +3 погіршені копії, 13 completed аналізів і17 подій. Це демонстрація, незалежність сцен не підтверджена. [Звіт, manifest і помилки](reports/firesense/REPORT.md). [Підсумковий звіт, метрики й screenshot](reports/ml/final-verification-20261102/REPORT.md). Стек: FastAPI, React + TypeScript + Vite, PostgreSQL; API та БД мають окремі health endpoints.

## Середовище

Зони спостереження, часовий алгоритм і журнал уже реалізовані: редактор на `/analysis`, реальні події/картки/оцінка на `/events`, defaults нових запусків на `/settings`. [Інструкція та API](docs/EVENTS.md), [фактичні перевірки й скриншоти](reports/events/REPORT.md). Міграція `0004_zones_events` застосована. Ізольовані тести й TypeScript/build пройдені; наступним етапом отримано FIRESENSE і виконано реальну демонстрацію часових подій на неперервних відео: [результати](reports/firesense/REPORT.md). Незалежна наукова оцінка лишається невиконаною; val-слайд-відеоряд її не підміняє. Для повторення ізольованих перевірок: `scripts/check-events.ps1`.

Модуль «Аналіз відео»: [повна інструкція, API, черга, формати та межі перевірки](docs/ANALYSIS.md). Окремий worker запускається `.\scripts\start-analysis-worker.ps1`; реєстрація моделі — `.\scripts\register-model.ps1 -Report '<підсумковий report.json>' -Name '<назва>'` **лише після завершення навчання та перевірки фінальних ваг**. Під час навчання залишати `ANALYSIS_ALLOW_GPU=false`; поточні checkpoints не реєструвати.

Перевірено у Windows PowerShell 5.1: Python 3.12.8 (64 біти), pip 24.3.1 у `.venv`, Node.js 24.13.0, npm 11.6.2, PostgreSQL 17.9. Скрипт підготовки використовує Python 3.12 через `py`; можна передати шлях явно. Сам API та сторінка запускаються й без налаштованої БД. Повний огляд обладнання та обмежень — у [PROGRESS.md](PROGRESS.md).

Версії зафіксовано в `backend/requirements.txt` (включно з транзитивними залежностями) та `frontend/package-lock.json`. Зокрема: FastAPI 0.162.0, Uvicorn 0.54.0, React 19.3.1, TypeScript 7.0.2, Vite 8.3.5.

## Підготовка

У Windows PowerShell:

```powershell
Set-Location D:\FireVision
.\scripts\setup.ps1
```

Або з явним вибором установленого інтерпретатора:

```powershell
.\scripts\setup.ps1 -PythonExecutable 'C:\Users\testuser\AppData\Local\Programs\Python\Python312\python.exe'
```

Скрипт перевіряє/створює базове `.venv`, а серверні пакети встановлює через `scripts/setup-api.ps1` **в окреме `.venv-api`**. Існуюче ML-середовище `.venv` не змінюється. Також виконує `npm ci` у `frontend` та копіює `.env.example` у `.env`, якщо файла ще немає. Наявні `.env` і неповні середовища автоматично не перезаписуються. Активувати середовища не потрібно. На вже підготовленому проєкті для нового API достатньо `.\scripts\setup-api.ps1`; під час навчання не виконуйте setup-ml чи перевстановлення пакетів у `.venv`.

Кеші: `D:\FireVision\.cache\pip`, `D:\FireVision\.cache\npm`. Тимчасові файли дочірніх процесів: `D:\FireVision\.tmp`. Скрипти встановлюють змінні лише для поточного процесу та нащадків, а після завершення відновлюють попередні значення. Системні/користувацькі PATH, TEMP/TMP і глобальні конфігурації pip/npm не змінюються. Для додаткових проєктних команд використовуйте ту саму обгортку:

```powershell
. .\scripts\project-env.ps1
Use-ProjectEnvironment {
    Invoke-ProjectCommand '.\.venv\Scripts\python.exe' @('-m', 'pip', 'check')
}
```

## Запуск

Перше вікно PowerShell:

```powershell
Set-Location D:\FireVision
.\scripts\start-backend.ps1
```

Друге вікно PowerShell:

```powershell
Set-Location D:\FireVision
.\scripts\start-frontend.ps1
```

Відкрити <http://127.0.0.1:5173>. Зупинення кожного процесу — `Ctrl+C` у відповідному вікні. Порти інтерфейсу фіксовані: зайнятий 5173 викликає помилку, без прихованого переходу на інший порт.

API: <http://127.0.0.1:8000/api/health>, документація: <http://127.0.0.1:8000/docs>.

```powershell
Invoke-RestMethod http://127.0.0.1:8000/api/health
```

Відповідь: `{"status":"ok","service":"api"}`. Перевірка стосується працездатності API. База даних і нейромережа не перевіряються.

Окрема перевірка `GET /api/health/db` виконує реальний `SELECT 1`: HTTP 200 і `{"status":"ok","service":"database"}` за доступної БД; HTTP 503 і `{"status":"unavailable","service":"database"}` за відсутньої конфігурації або недоступного підключення. Відповідь не підтверджує актуальність міграцій, наявність моделі чи готовність оброблення відео.

| `ANALYSIS_MAX_PIXELS` | `8294400` | Максимум пікселів кадру для аналізу (3840 × 2160) |

Vite читає `.env` із кореня через `envDir`. Після зміни конфігурації перезапустіть відповідний компонент; для production потрібна повторна збірка. Змінні `VITE_*` потрапляють у браузер — секрети в них не зберігати.

Значення `.env.example` для користувача й пароля — заповнювачі. Для БД заповніть локальний `.env` даними наявного користувача. Нові ролі та паролі скрипти не створюють. Пароль обов’язковий; порожнє значення не запускає спробу підключення без пароля. Змінні процесу мають пріоритет над `.env`.

Пароль можна взяти в одинарні лапки; всередині них `\'` означає одинарну лапку, `\\` — зворотну скісну риску. Інтерполяцію `${...}` вимкнено. SQLAlchemy отримує `URL.create` з окремими полями; URL не записується в `alembic.ini`, тому `%`, `@`, `:`, `/`, `#` не проходять додаткову інтерполяцію ConfigParser. Не потрібно вручну URL-кодувати пароль.

Сторінка показує початкове очікування, підключення або помилку. Після кожного завершеного запиту повторює перевірку через 3 секунди; тайм-аут запиту — 4 секунди. Втрата зв’язку та відновлення підключення відображаються автоматично.

## Перевірка

```powershell
Set-Location D:\FireVision
.\scripts\check.ps1
```

Команда перевіряє `pip check`, TypeScript, production build і браузерний сценарій. Для браузерної перевірки потрібен установлений Microsoft Edge: використовується локальний `playwright-core`, завантаження браузера не виконується. Перевірка запускає власні процеси на портах 18000 і 15173, перевіряє HTTP-відповідь, CORS, очікування, реальне підключення та помилку після зупинення API. Власні процеси закриваються; зайняті тестові порти спричиняють відмову. Звіт — `.tmp/smoke-results.json`.

Окремо перевірити збірку:

```powershell
Set-Location D:\FireVision
. .\scripts\project-env.ps1
Use-ProjectEnvironment {
    Push-Location frontend
    try { Invoke-ProjectCommand 'npm.cmd' @('run', 'build') } finally { Pop-Location }
}
```

Результат — `frontend/dist`. Перевірка вручну: запустити обидва компоненти, відкрити сторінку, дочекатися «API підключено», зупинити API та дочекатися «Не вдалося підключитися до API».

## Створення БД та міграції

Після заповнення `.env`:

```powershell
Set-Location D:\FireVision
.\scripts\db.ps1 create
.\scripts\db.ps1 upgrade
.\scripts\db.ps1 current
.\scripts\db.ps1 check
```

`create` використовує наявного користувача: у службовій БД `postgres` перевіряє існування цільової БД, за потреби створює лише `firevision_db` з UTF-8 через `template0`, далі перевіряє її таблиці й ревізію. Потрібні CONNECT і, для створення, CREATEDB. Якщо права відсутні, базу має створити адміністратор; автоматичної зміни прав немає. Невідома наявна схема зупиняє команду. Чинні бази не видаляються й не очищаються.

`upgrade` — Alembic `upgrade head`, повторне виконання безпечне. `current` показує поточну ревізію; `check` порівнює схему з ORM. Поточна ревізія — `0002_video_metadata`: до початкової схеми додано чотири nullable-поля контейнера, кодека й частот кадрів. Усі зміни схеми виконуються міграціями, окремо від запуску API; наявні таблиці не перебудовуються.

SQL без підключення до PostgreSQL:

```powershell
.\scripts\db.ps1 sql
```

## Початкова схема

| Таблиця | Дані й типи |
| --- | --- |
| `video_sources` | UUID `id`; назва varchar(255), оригінальне ім’я та відносний шлях text; розмір bigint, SHA-256 varchar(64); тривалість numeric(16,6), ширина/висота integer, FPS numeric(12,6); `created_at` timestamptz |
| `model_versions` | UUID `id`; назва varchar(255), архітектура varchar(128); шлях text і SHA-256 varchar(64) ваг; JSONB `class_mapping` та `training_metadata`; `created_at` timestamptz |
| `analysis_runs` | UUID `id`, два FK; `mode`, `status` varchar(24); обов’язковий JSONB `settings_snapshot`; прогрес numeric(6,5); помилка text; технічні часи timestamptz; JSONB `summary_metrics`, `result_paths` |
| `events` | UUID `id`, FK на запуск; тип ознак і автоматичний стан; початок/підтвердження/завершення numeric(16,6) у секундах відео; упевненість numeric(6,5), JSONB області; шляхи кадру/фрагмента text; окремий статус перевірки й коментар; `created_at`, `updated_at` timestamptz |

UUID генерується застосунком. Дати створення мають серверний `now()`. Невідомі розмір, SHA-256, тривалість, ширина, висота й FPS відео — `NULL`, без нульових підстановок. У моделі обов’язкові перевірені ваги й непорожня відповідність класів; JSON-ключі номерів класів — десяткові рядки, наприклад `"0"`. Порядок `fire`/`smoke` не закріплено. `training_metadata` типово `{}` і не означає виконаного навчання.

Додаткові nullable-поля `video_sources`: `container_format` varchar(255), `video_codec` varchar(128), `avg_frame_rate` і `r_frame_rate` varchar(64). Останні зберігають вихідні раціональні значення ffprobe; `fps` — числове середнє з `avg_frame_rate`, не припущення сталої частоти.

Зв’язки: `video_sources 1 → N analysis_runs`, `model_versions 1 → N analysis_runs`, `analysis_runs 1 → N events`. `events` не дублює ідентифікатор джерела. FK мають `ON DELETE RESTRICT`, щоб випадкове видалення не знищувало історію. `alembic_version` — службова таблиця.

Режими запуску: `playback`, `full`; стани: `pending`, `running`, `stopped`, `completed`, `failed`. Помилка, початок/кінець запуску, метрики й результати допускають `NULL`. Прогрес — частка 0–1, початково 0; це стан виконання, не метрика детектора. JSON-знімок налаштувань обов’язковий, його зміни блокує тригер БД.

Тип події: `fire` або `smoke`; автоматичні стани: `suspected`, `confirmed`, `completed`. Початок обов’язковий; підтвердження й кінець можуть бути `NULL` відповідно до стану. Часові позначки впорядковані й невід’ємні. Об’єднання полум’я й диму в один епізод поки не реалізовано. Упевненість 0–1, область, кадр і фрагмент можуть бути `NULL` до підготовки результатів. Формат JSON області буде уточнено на етапі просторового аналізу; нині вимагається JSON-об’єкт. Перевірка оператора незалежна: `unreviewed`, `confirmed`, `false_positive`, `needs_review`; коментар nullable. Тригер оновлює `updated_at` при UPDATE.

Індекси: FK запуску на джерело й модель; події за `(analysis_run_id, start_seconds)`; дати створення джерел/моделей; SHA-256; `(status, created_at)` запусків; автоматичний стан подій і `(review_status, created_at)`. SHA-256 не унікальний: той самий файл може брати участь у кількох записах. Обмеження перевіряють контрольні суми, розміри, діапазони, JSON-об’єкти та відносні шляхи.

У `result_paths` зберігається плоский JSON-об’єкт «назва артефакту → відносний шлях». Скаляри шляхів та значення `result_paths` перевіряються БД: без диска, початкового `/`, зворотних скісних рисок, порожніх компонентів, `.` та `..`. Формат — `videos/...`, `weights/...`, `results/...` відносно `STORAGE_ROOT`. `storage_path()` додатково перевіряє вихід за корінь, у тому числі через посилання. Абсолютні локальні шляхи не записувати також у довільні JSON-метадані.

## Перевірки БД

Без доступу до БД (онлайн-перевірки пропускаються):

```powershell
.\scripts\check-db.ps1
```

З налаштованою БД після міграції:

```powershell
.\scripts\check-db.ps1 -WithDatabase
```

Перевіряються реальний SELECT 1, схема, ревізія, український текст, nullable-метадані, FK, RESTRICT, діапазони, відносні шляхи, незмінність налаштувань та health endpoints (200/503). Тестові предметні записи завжди відкочуються зовнішньою транзакцією. HTTP-тести запускають власний сервер на вільному порту й зупиняють його. Окремо перевіряються спеціальні символи синтетичного пароля без зміни справжнього пароля.

## Резервна копія та перенесення

Custom backup містить БД; відео, ваги й результати потрібно переносити окремо. Ролі кластера не експортуються, `pg_dumpall` не використовується. Скрипти передають чинний пароль тільки через середовище дочірнього процесу, без виведення секретів чи URL. `--no-password` у командах утиліт вимикає інтерактивний запит, а не автентифікацію.

Створення нової копії (наявний файл не перезаписується):

```powershell
Set-Location D:\FireVision
New-Item -ItemType Directory -Path .\backups -Force
.\scripts\db.ps1 backup -File .\backups\firevision-2026-11-01.dump -PgBin 'C:\Program Files\PostgreSQL\17\bin'
```

Використовується `pg_dump --format=custom`. Для іншого ПК установіть сумісний PostgreSQL і Python/Node, перенесіть код, виконайте `setup.ps1`, заповніть `.env` чинними обліковими даними цього ПК. Потім **створіть порожню БД без upgrade перед відновленням**:

```powershell
.\scripts\db.ps1 create
.\scripts\db.ps1 restore -File .\backups\firevision-2026-11-01.dump -PgBin 'C:\Program Files\PostgreSQL\17\bin'
.\scripts\db.ps1 current
.\scripts\db.ps1 upgrade
.\scripts\db.ps1 check
```

Відновлення виконує `pg_restore --no-owner --no-acl --exit-on-error --single-transaction` у вже створену порожню `firevision_db`; непорожня БД відхиляється. `--clean` не використовується. Відновлення на чинній БД під час тестів не проводиться. Для перенесення використовуйте PostgreSQL тієї самої або новішої сумісної версії та перевіряйте версії клієнтських утиліт.

Окремо скопіюйте папки `<STORAGE_ROOT>/videos`, `<STORAGE_ROOT>/weights`, `<STORAGE_ROOT>/results`, зберігаючи відносну структуру, і встановіть новий `STORAGE_ROOT`. Ці папки ще не наповнювалися на цьому етапі. Локальні `.env`, датасети, ваги, результати й дампи виключені з Git.

Перевірка custom backup/restore на поточному ПК:

```powershell
.\scripts\check-db-transfer.ps1 -PgBin 'C:\Program Files\PostgreSQL\17\bin'
```

Команда потребує CREATEDB, створює окрему БД з випадковим ім’ям `firevision_restore_check_*`, відновлює туди копію, перевіряє схему, ревізію, UTF-8, FK, тригери й кількості записів, після чого видаляє тільки власну тимчасову БД і тестовий дамп. Доступ CREATEDB не надається автоматично. Цю перевірку успішно виконано; перенесення на інший фізичний ПК ще не перевірялося.

## Відеоджерела: підготовка та ручна перевірка

```powershell
Set-Location D:\FireVision
.\scripts\setup.ps1
.\scripts\setup-ffmpeg.ps1
.\scripts\db.ps1 upgrade
.\scripts\db.ps1 check
```

Portable FFmpeg/ffprobe встановлюються у `tools/ffmpeg/bin` без зміни PATH. Зафіксована збірка — Gyan release essentials 9.0.2 із посилання на офіційному сайті FFmpeg; джерело, SHA-256 та особливості встановлення наведено в [tools/README.md](tools/README.md). Завантаження архіву перевіряється за SHA-256; перерваний файл у кеші можна дозавантажити повторним запуском скрипта. Якщо інструменти вже є в іншому місці, задайте їхні шляхи у `.env`.

У двох вікнах PowerShell запустіть `scripts/start-backend.ps1` та `scripts/start-frontend.ps1`, як описано вище. Відкрийте <http://127.0.0.1:5173>: введіть назву, виберіть файл і натисніть «Завантажити відео». Сторінка показує надсилання, перевірку/збереження, помилки, список із пагінацією та деталі вибраного джерела з плеєром. Після оновлення сторінки або перезапуску API список читається з PostgreSQL. Аналіз нейромережею не запускається.

API та інтерактивна документація: <http://127.0.0.1:8000/docs>.

| Метод і шлях | Призначення |
| --- | --- |
| `POST /api/video-sources` | Multipart: текстове поле `name`, файл `file`; HTTP 201 після перевірки й commit |
| `GET /api/video-sources?page=1&page_size=20` | Список: `items`, `total`, `page`, `page_size`, `upload_limit_bytes`; page >=1, page_size 1–100 |
| `GET /api/video-sources/{id}` | Деталі за UUID; невідомий UUID — 404, некоректний формат UUID — 422 |
| `GET /api/video-sources/{id}/content` | Відео за UUID з підтримкою Range; довільний файловий шлях не приймається |

Налаштований ліміт — **1 073 741 824 байти (1 ГіБ)**. Значення `UPLOAD_MAX_BYTES` можна змінити з перезапуском API. Ліміт перевіряється за фактично отриманими байтами файлу, також без Content-Length. Для multipart-заголовків і текстового поля допускається до 64 КіБ додаткового тіла; кількість полів і заголовки також обмежені. Назва джерела: 1–255 символів. Для потокового парсера використовується `python-multipart` 0.0.33.

Оригінали: `<STORAGE_ROOT>/videos/originals/<uuid>.<розширення>`. Тимчасові файли запиту: `<STORAGE_ROOT>/tmp/uploads/<uuid>.part`, у поточній конфігурації також на D:. Ім’я оригінального файлу зберігається лише як метадані, каталог від клієнта відкидається. Розширення збереженого файлу обирається за контейнером ffprobe. Тіло запиту не читається цілком в RAM: multipart парситься порціями, файл пишеться на диск, одночасно рахується SHA-256 і розмір.

Після завершення завантаження ffprobe запускається списком аргументів без shell, із тайм-аутом. Перевіряється наявність відеопотоку; обкладинка аудіофайлу не вважається відео. Невідомі параметри залишаються `NULL`. Для VFR зберігаються середня й базова раціональні частоти; їхня різниця сама по собі не використовується як доказ VFR. Вибирається перший відеопотік, який не є attached picture; середня частота не підміняє часові позначки кадрів у майбутньому аналізі.

Дозволені локальні контейнери, які підтримує встановлений ffprobe: сімейство MOV/MP4, Matroska/WebM, AVI, ASF, MPEG, MPEG-TS, Ogg і FLV. Розширення й MIME від клієнта не є доказом формату. Мережеві протоколи та інші демультиплексори, зокрема плейлисти із зовнішніми сегментами, не дозволені. Сам факт прийняття файлу не гарантує декодування його кодека браузером: плеєр явно повідомляє про непідтримуваний формат або помилку декодування. Автоматичного перекодування немає. Тестовий сценарій використовує MP4/H.264, yuv420p у встановленому Edge.

Порожній файл, пошкоджений/непідтримуваний файл, відсутність відеопотоку й тайм-аут перевірки повертають 422; перевищення розміру — 413; некоректна multipart-форма — 400; недоступний інструмент, сховище чи БД — безпечний 503. Збій ffprobe або збереження спричиняє очищення файлів цього запиту. Завершений файл переміщується перед commit БД; немає успішної відповіді до commit. Аварійне завершення процесу/ОС між операцією файлової системи й commit не має спільної транзакції; автоматичне звіряння після таких аварій поки не реалізовано. ffprobe перевіряє контейнер і доступні метадані, не виконує повного декодування всього запису, тому приховані дефекти пізніх кадрів можуть виявитися під час відтворення.

Віддавання виконується [Starlette FileResponse](https://starlette.dev/responses/#fileresponse): `Accept-Ranges: bytes`, HTTP 206 для коректного діапазону та 416 для діапазону поза файлом. Шлях береться з БД й перевіряється відносно кореня сховища. Відсутній фізичний файл повертає 404.

## Перше повне навчання YOLO11n

Поточний базовий експеримент: `runs/full/yolo11n_baseline_20261101T203432Z_b1931c45`. Це навчання моделі для розроблення: незалежність сцен val/test не доведена, val використовується для вибору checkpoint. Дозволу на YOLO11s, незалежну тестову оцінку чи підключення ваг до застосунку немає.

Весь погоджений **train 7238 / val 1436**, без test і без технічної підмножини. Вихідна точка — офіційні `weights/pretrained/yolo11n-v8.3.0.pt`, SHA-256 `0ebbc80d4a7680d14987a577cd21342b65ecfd94632bd9a8da63ae6417644ee1`. Шляхи, версії, склад, SHA-256 основних і окремих списків та початкова перевірка всіх 8674 пар image/label — у `readiness.json`, `input/`, `input-verification-before.json`. Списки посилаються на оригінали без копій зображень. Файли test-зображень не читаються.

Базові параметри: **epochs=50, patience=10, imgsz=640, batch=4, device=0, workers=0, amp=true, cache=false, optimizer=AdamW, lr0=0.001, seed=42, save=true, save_period=1**, deterministic=true. Це перший базовий експеримент, а не підібрані оптимальні параметри. Параметри перевірено через `get_cfg` Ultralytics 8.4.197; повний фактичний конфіг — `training/args.yaml`, усі початкові значення — `configuration.json`, optimizer — `optimizer-runtime.json`.

Планувальник LambdaLR лінійний (`cos_lr=false`, `lrf=0.01`): `max(1-epoch/50,0)*(1-lrf)+lrf`; warmup 3 епохи, warmup_momentum=0.8, warmup_bias_lr=0.1. AdamW beta1=0.937, beta2=0.999, weight_decay=0.0005 для ваг; nbs=64 і накопичення градієнтів керуються бібліотекою (після warmup batch=4 дає 16 кроків накопичення). **Best обирається за максимумом val mAP50–95**; при точній рівності бібліотека записує пізнішу епоху. Patience=10 використовує цей fitness.

Аугментації детекції: hsv_h=0.015, hsv_s=0.7, hsv_v=0.4, translate=0.1, scale=0.5, fliplr=0.5, mosaic=1.0; mosaic вимикається за 10 епох до запланованого кінця. degrees/shear/perspective/flipud/bgr/mixup/cutmix/copy_paste=0. Значення auto_augment/erasing у повному конфігу є загальними параметрами бібліотеки для класифікації; вони не означають застосування цих аугментацій до цього detection-run.

Новий запуск (створює унікальну папку; не виконуйте, поки поточний працює):

Процес працює окремо від FastAPI у прихованому вікні. Кеші й тимчасові файли успадковують локальне середовище D:. Точна команда дочірнього процесу, PID і SHA-256 скрипта — `command-session_*.json`; копія початкового коду поточного запуску — `code/`. Два процеси для однієї папки або паралельні проєктні GPU-запуски заборонено блокуваннями ОС. Після аварійного завершення блокування звільняється ОС; `Status` показує відсутність живого процесу.

Перевірка поточного запуску (після нового Start типовий вказівник зміниться, тому для цього експерименту задавайте RunDir явно):

`state.json` оновлюється кожні 32 train-batch та на межах епох. Completed_epochs змінюється після валідації та запису checkpoint. `epoch-times.jsonl` містить виміряні тривалості повних епох; ETA у Status — до 50 без прогнозування early stopping. Динамічна телеметрія PyTorch містить максимальні allocated/reserved і поточну вільну пам’ять; nvidia-smi показує весь пристрій, включно з іншими програмами.

Відновлення **лише після переривання**, без запуску другого процесу:

```powershell
.\scripts\train-full.ps1 -Action Inspect -Checkpoint "$run\training\weights\epoch0.pt"
.\scripts\train-full.ps1 -Action Resume -RunDir $run
```

Resume перевіряє завантаження, скінченність ваг і optimizer state, класи 0=smoke / 1=fire, номер епохи, належність data.yaml і незавершений план епох. Спочатку перевіряє last.pt, потім resume-last.pt і періодичні epochN.pt від нових до старих. `epoch0.pt` — кінець першої епохи. Відхилені кандидати й вибір записуються в `resume-selection.json`. Перед продовженням попередні ваги/CSV зберігаються в `resume-history/`; CSV відновлюється з train_results вибраного checkpoint, best — з відповідної справної епохи. Артефакти пізніших епох не змішуються з повтореним відрізком. Це відновлення optimizer, AMP scaler, EMA і early-stopping state; scheduler реконструюється з того самого плану та номера епохи. Побітова тотожність безперервному запуску не гарантується: checkpoint бібліотеки не зберігає всі RNG/loader стани.

У цій версії Ultralytics фіналізація **видаляє optimizer і встановлює epoch=-1 у best.pt/last.pt**. Тому inference-ваги після завершення не приймаються як resume. Періодичні checkpoint залишаються повними; перед фіналізацією worker також зберігає `resume-last.pt`. Завершений експеримент не продовжується цим Resume: новий план донавчання лише з ваг — окремий експеримент за окремим завданням.

При NaN/Inf або CUDA OOM worker записує помилку й зупиняється; внутрішнє автоматичне зменшення batch та приховані повтори епох вимкнено. CPU fallback немає. Якщо OOM підтверджено, команда підготовки нового експерименту: `.\scripts\train-full.ps1 -Action Start -Batch 2`. Це змінює конфігурацію, накопичення градієнтів і порівнянність запусків; причину й попередню помилку потрібно включити до звіту. У поточному запуску batch не змінювався.

Захист оригіналів: локальна read-only перевірка PIL, label-cache у `.cache/ultralytics-labels`, SHA-256 до старту, після першої повної епохи та після завершення. Перед повним запуском виправлено порядок PIL verify/exif: exif_size до verify помилково відхиляв PNG із JPEG-розширенням. Додано регресійний тест, новий namespace кешу v2; попередню невдалу підготовку `yolo11n_baseline_20261101T203010Z_08f4d36b` збережено (0 епох). Дані й основні маніфести не змінювалися.
