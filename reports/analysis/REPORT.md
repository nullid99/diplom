# Модуль «Аналіз відео» — 02.11.2026

## Реалізовано

Backend/frontend для повного сценарію після реєстрації перевіреної моделі. API моделей і запусків, незмінні параметри, PostgreSQL-черга з атомарним admission/claim та одним власником worker, прогрес/heartbeat, запит і підтвердження скасування, виявлення аварії за DB lock, захищена публікація готових файлів. Окремий worker закриває ресурси, не переходить автоматично на CPU й не змінює параметри. Реєстрація — локальна команда тільки для перевірених фінальних best.pt завершеного full-run.

Підготовлено адаптер Ultralytics і медіапроцесор: послідовний декодер, окремі пороги smoke/fire, відбір за часом, поступовий JSONL та H.264 MP4, збереження всіх кадрів і вихідних VFR-інтервалів, перевірка кожного PTS/кількості кадрів/тривалості. Результати мають відносні шляхи в БД; детекції не записуються окремими SQL-рядками. UI відновлює стан із API/БД та WebSocket після reload/reconnect; часткових результатів не показує.

Міграція `0003_analysis_worker` застосована до firevision_db, повторний upgrade head пройшов, Alembic check не знаходить розбіжностей. Додано лише worker_id/heartbeat_at/cancel_requested_at та захист входів від змін; стани pending/running/completed/failed/stopped і чотири предметні таблиці збережено.

Для API створено окреме `.venv-api` з wsproto 1.3.2 та зафіксованими легкими backend-пакетами. ML `.venv` не перевстановлювали. Кеші аналізу ізольовані в `.cache/analysis`; GPU аналізу вимкнено за замовчуванням і додатково захищено тим самим проєктним GPU lock. Файли/датасет/ваги/конфігурація активного навчання не редагувалися.

- **17 тестів аналізу** в окремій `firevision_analysis_test_*`: API/відсутність моделі, параметри/SHA/черга, незмінний snapshot, конкурентні claim/capacity, duplicate worker, активне й очікуване скасування, дійсний аварійний child-process, виявлення втрати власника через API, відмова COMMIT без готових залишків, cleanup/resources, VFR і довільна тривалість останнього кадру, JSONL/готові файли, HTTP Range, окремі smoke/fire пороги адаптера, живий прогрес і перепідключення WS. Реєстрація активного run відхиляється до імпорту ML/читання ваг.
- Реальний Edge із вимкненими GPU та hardware video decode: порожній стан, disabled start, створення/скасування тестового pending, reload, WebSocket reconnect, перегляд/seek/download готового **тестового** результату. Детектор — тільки fixture із tests, не YOLO; тестова БД видалена. Матеріали в `.tmp/analysis-test-*` не є робочими даними або датасетом.
- **9 попередніх БД/API + 7 попередніх відеотестів**, включно з upload/reload/seek, health/CORS, базовий browser smoke (очікування → API connected → помилка після зупинки тестового API).
- TypeScript, production build, pip check ML і API. Точні версії ML збігаються з початковим lock; не встановлювали PyTorch/Ultralytics/OpenCV або нові пакети в ML `.venv`.

## Залишилося перевірити після реєстрації моделі

1. Дочекатися фактичного завершення навчання, сформувати/переглянути фінальний full-training report; тільки після цього зареєструвати перевірений best.pt.
2. Реальний Ultralytics forward на CPU та, коли дозволено й вільно, на GPU; фактичні класи, пороги, пам’ять/помилки.
3. Наскрізний upload → справжня модель → queue/worker → детекція → файли → браузер на короткому реальному відео; візуально зберегти успіхи/пропуски/хибні рамки.
4. Зіставити часові мітки й результати на реальному матеріалі та перевірити скасування/ресурси під реальним ML-навантаженням.

Ці перевірки **не виконані**, повний сценарій із реальною YOLO не оголошується перевіреним. Немає реальних аналізів, зареєстрованих пробних/COCO моделей, вигаданих метрик або подій. Test не використовувався; незалежність сцен не підтверджена. Зони, часові події та моніторинг кількох джерел не реалізовані.

Обмеження версії: вихідний MP4 без звуку/субтитрів; rotation metadata, змінні розміри в одному потоці, перший потік-обкладинка та зсув початку відео/контейнера понад 10 мс відхиляються. Невідомі/незростаючі часові мітки не підміняються CFR. Максимум 8 294 400 пікселів кадру; черга 10; I/O timeout 60 с. Рамки є тільки на реально проаналізованих кадрах, між ними tracking/домальовування не виконується. Повні команди й API — [docs/ANALYSIS.md](../../docs/ANALYSIS.md).
